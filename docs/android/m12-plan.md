# M12 plan (DRAFT): standalone APK, no Termux

Goal: one APK. The user installs it, grants the permissions it asks for, logs in to Claude, and uses the app. No Termux, no `lh`, no `adb`, no developer toggles if it can be avoided. The Claude subscription stays (the `claude` CLI keeps running on the device).

## Decisions (owner, 2026-10-28)

| Topic | Decision |
|---|---|
| Subscription | Kept. The `claude` CLI runs on the device; no API-key-only path |
| Delivery | The APK is small. On first run it downloads the rootfs + server tarball (the `android-latest` CI artifact) with a progress screen. The same download is the update path |
| Headless rendering | Chromium is replaced by the system WebView now. An Android `HeadlessApi` implementation (`runDemo`, `renderSvg`, `renderPdf`) plugs in through `headlessOverride` (`src/agent/subagents/headless.ts`) |
| Render bridge | A token-authenticated loopback HTTP service in the Kotlin shell. The Node server posts jobs and gets PNG, console errors and probe results back. Offscreen WebView for demos and SVG; Android `PdfRenderer` for PDFs |
| **Render bridge scope (changed, owner approved 2026-10-28)** | The bridge shrinks to one endpoint, `POST /run-demo`. `renderSvg` already renders with resvg in Node and `renderPdfPages` with pdfjs + `@napi-rs/canvas` in Node (Chromium is only the SVG fallback), so the Android `PdfRenderer` leg above is dropped. Subject to gate E showing that the linux-arm64 builds of `@resvg/resvg-js` and `@napi-rs/canvas` load |
| Dictation | Android `SpeechRecognizer`, **on-device only** (no cloud fallback; a missing language pack starts Android's download and says so), multiplexed on the existing `lhAndroid` channel as `speech ...` lines, **automatic** in the Android shell (the page asks `speech probe`; no new setting). No whisper build or model download |
| Model slots | Android seeds the three slots on a fresh install: strong `claude-opus-5-5`, cheap `claude-haiku-5-5`, vision `claude-sonnet-5-5` (provider `claude-code`); desktop and browser keep the no-defaults rule |
| Rootfs source | CI-built release asset `learnharness-rootfs-linux-arm64.tar.gz` in its own rolling release `android-rootfs` (the server workflow recreates `android-latest` on every run) |
| Claude binary | Not redistributed: installed from npm on the phone at the version the app pins (`Release.CLAUDE_VERSION`), into the home, so a rootfs update keeps it |
| Existing data | Start fresh; no migration from the Termux install |
| Claude CLI version | Pinned per app release; installed at first run and when the pin changes; no auto-update |

## Shape

- The shell unpacks a minimal Linux rootfs (Node 26, the Next standalone server, `claude`) into private storage and runs it under proot (or a glibc loader if that proves faster). `proot` and its loader ship in the APK as native libraries.
- The shell starts and supervises the server itself (foreground service) and pairs in-process. Termux, `RUN_COMMAND` and `lh` are no longer used.
- Claude login: the shell runs `claude auth login` on a pty, opens the URL in the browser, and takes the code in its own field.
- Dictation: whisper built with the NDK, or Android `SpeechRecognizer`. Not decided here.

## Open risks (what the spike must answer first)

1. **Phantom-process killer (Android 12+).** Child processes of an app can be killed, also with the screen off. If the only fix is a Developer-options toggle or `adb`, the "no setup" goal fails. M0 left this untested.
2. **Executing `proot` from the APK's native-library directory** at a current target SDK on Android 17.
3. **Memory** of server + `claude` + whisper + WebView against about 2-3 GB free on the Pixel 7 Pro.
4. **Download size** of rootfs + `claude` + models.

## Step 0: gating spike (debug only, throwaway)

Nothing else is built until every gate passes. All spike code lives under `android/app/src/debug/` (activity, foreground service, `jniLibs`), like the M9/M10 spikes; `MainActivity`, `Termux.kt` and the main manifest are not touched. The one build-file change is `packaging { jniLibs { useLegacyPackaging = true } }` so the native libraries are extracted to `nativeLibraryDir`.

**Rootfs for the spike.** No download or unpack code. A fresh Ubuntu 24.04 arm64 base rootfs plus the Node 26 linux-arm64 tarball (as in M0) are pushed with `adb push` to `/data/local/tmp` and unpacked into the app's `files/` with `run-as dev.learnharness.android`. This also exercises the provisioning the real first-run download has to do.

| Gate | Question | Pass | Fail means |
|---|---|---|---|
| A | Can `proot` run from `nativeLibraryDir` at targetSdk 37 (Android 17) and start a guest ELF that sits in the app's private storage? | `proot ... /bin/true` exits 0, then `node --version` in the guest prints Node 26 | Owner decision: targetSdk 28 (what Termux does; changes WebView/storage behavior of the whole shell), or another exec route. Stop and report |
| B | Does `claude` run in that guest and do a real stream-json round trip? | `claude --version`, then one haiku turn with the subscription login | Stop and report |
| C | Does the whole tree survive with the screen off? | 30 min, phone unplugged and screen off, `dumpsys deviceidle force-idle`, a foreground service (type `specialUse`) with a partial wake lock: every PID alive at the end, heartbeat gaps of 60 s or less, no `PhantomProcess` kill lines in logcat | Stop and report; the fix would be a user-visible toggle, which the owner must accept |
| E | Does the real harness run? (added after the advisor review) | Download the `android-latest` tarball, check its `.sha256`, unpack it in the guest (`zstd` added by `dpkg -x` as `libatomic1` was), start `node server.js` from the spike service with the `lh` env contract, no `CHROME_PATH` and `LH_ACCESS_TOKEN` unset; open the UI in a WebView and run one tutoring turn that makes a tool call through `claude` | The MCP stub + loopback bridge fail under proot, or the native modules do not load: the architecture changes |
| D | Does it fit in memory? | Tree RSS (server stand-in + `claude` + whisper) logged every 30 s next to `MemAvailable`; no low-memory kill | Report the numbers; the Chromium-to-WebView swap is already decided |

**Method notes.**
- *proot source.* Termux's own `proot` is linked against `libtalloc` and Termux paths, so it is not copied over. Needed: a build with no `$PREFIX` dependency (static, or proot plus talloc each shipped as `lib*.so`), and the loader shipped as `lib*.so` too (`PROOT_LOADER`, `PROOT_TMP_DIR` in the app's cache). Checked with an ELF dump before use.
- *Is a pass meaningful?* Before the screen-off run the phone must have default phantom-process settings (`settings_enable_monitor_phantom_procs`, `max_phantom_processes`, the "Disable child process restrictions" toggle; first two read as unset on 2026-10-28) and the Termux `lh` server (whisper, supervisor, proot guest) must be stopped, because its tree shares the same limit and memory. Stopping it touches the owner's working setup, so it is asked first.
- *Heartbeat.* The service appends time, PIDs and RSS to a file in `files/` every 30 s; the verdict is read from that file and from logcat afterwards.
- *Credentials.* Gate B needs a Claude login inside the spike's guest (a fresh login, or a copy of the owner's `~/.claude`); asked, not assumed.

### Spike results (2026-10-28, Pixel 7 Pro, Android 17 / SDK 37, APK targetSdk 37)

- **Gate A: PASS.** `proot` runs from `nativeLibraryDir` (`useLegacyPackaging = true`; the libs sit in `/data/app/.../lib/arm64` as `apk_data_file`), and starts guest ELFs that live in the app's private `files/`: `/bin/true`, `uname`, and Node 26.12.1 (after `libatomic1`). targetSdk 28 is **not** needed.
  - **proot source matters.** The green-green-avk build (2023) fails at the first guest exec (an unknown syscall, `void(AT_FDCWD, ...)` returning ENOENT, most likely `execveat`). Termux's own `proot` 5.1.107.101 works. Shipped as: `libproot.so` (Termux `bin/proot` with the `NEEDED` entry `libtalloc.so.2` rewritten in place to `libtalloc.so`), `libtalloc.so` (Termux libtalloc 2.5.0), `libandroid-shmem.so` (Termux 0.7), `libproot-loader.so` (Termux `libexec/proot/loader`); `LD_LIBRARY_PATH` = `nativeLibraryDir`, `PROOT_LOADER`, `PROOT_TMP_DIR` set by the service. All three Termux packages were checked against the sha256 in the official Termux index. GPL source-offer obligations apply before this ships.
  - **Rootfs gotchas.** Android's `tar` cannot create hard links (the Ubuntu base has two; the first-run unpacker must write them as copies); `dpkg` in the guest needs `PATH` set; `libatomic1` needs a zstd-aware unpack (`dpkg -x` inside the guest works).
- **Gate B: PASS.** `npm i -g @anthropic-ai/claude-code` in the guest (2.1.312). `claude auth login` under `script -qfc` with a fifo as stdin worked (the in-app login can do exactly this); one `claude -p` stream-json turn on haiku-5-5 with the subscription login took 7 s end to end. Not yet exercised: the MCP stub / loopback bridge path and an image block.
- **Gate C: PASS (with the caveat that it is 36 minutes, not hours).** 14:12:47 to 14:47:38, phone off the charger (battery 70 to 69 %), screen off, `deviceidle force-idle`, foreground service (`specialUse`) + partial wake lock, Termux force-stopped first. Three direct children of the app, each under proot: a ~400 MB Node server stand-in, a ~650 MB Node stand-in for whisper, and a live `claude` stream-json session fed one haiku turn every 5 minutes. Result: the same three PIDs alive at the end, no `EXIT` line, heartbeat gaps at most 31 s (30 s cadence), tick-file gaps at most 10.1 s on both Node processes (no CPU stalls), **7 of 7 claude turns completed, 0 errors**, no kill lines in logcat (the `PhantomProcessRecord ... died` lines are the feeder's 5-minute `sleep` exiting normally). The phone's phantom-process settings were at defaults (`settings_enable_monitor_phantom_procs` and `max_phantom_processes` unset), so the pass is meaningful. Not covered: hours-long runs, the user switching apps, battery saver, vendor-specific killers on other phones. Raw logs: scratchpad `gateC/`.
- **Gate E: PASS (2026-10-28).** The `android-latest` tarball (`0.3.6+60d9e57`, sha256 verified against the published `.sha256` and GitHub's digest) unpacked in the guest with `tar --zstd` (214 MB; `zstd` + `libzstd1` added with `dpkg -x`), and `node server.js` started under proot from the APK with the `lh` env, no `CHROME_PATH`, no token: Next.js 16.3.2 ready, `/api/health` `{"ok":true,"version":"0.3.6","tokenMode":false}`. Two real tutoring turns on `claude-code` / haiku-5-5 over `/api/chat` + the SSE stream: each ended with `agent_end` in about 4.5 s and made **two tool calls through the MCP stub and loopback bridge** (`list_sessions`, `ask_user_question`), so held tool calls work under proot. In the guest, `@resvg/resvg-js` renders a PNG, and `@napi-rs/canvas` and `pdfjs-dist` import (so `renderSvg` and `renderPdfPages` stay in Node and the bridge-narrowing above is supported by evidence). The app's own WebView (`MainActivity`, debug dev mode) rendered the real UI from the on-phone server (screenshot in scratchpad `gateE/ui.png`). **Process tree with the server and two live claude sessions: 6 processes (proot, next-server, 2 x (claude + MCP stub node)), 612 MB RSS, MemAvailable 3.77 GB** with Termux stopped and no visible UI load; the process count is far under the roughly 32 limit. Not covered: the image-result MCP path, a long real lesson, the demo render path (no `CHROME_PATH`, as planned), the pairing token mode, `renderPdfPages` on a real PDF.
  - **Finding for step 7:** a fresh data directory shows "Set up your models" with no model chosen (the provider pill reads "— · —"); the first-run flow must preselect the `claude-code` provider for the strong/cheap/vision slots, or the user sees an unconfigured app after login.
- **Process count.** The real tree adds a stdio MCP stub (a Node process) per `claude` session (up to 2) plus Next; Android's phantom limit is about 32 processes across all apps. Gate E records the real count. The supervisor starts proot directly with `ProcessBuilder`, not through `/system/bin/sh` (the spike spent a slot per child on the wrapper).
- **Supervisor lesson.** The spike's `stop` did `destroyForcibly()` on the `sh` wrappers and left the proot guests (node, `claude`) running; `--kill-on-exit` only fires when proot itself exits. The real supervisor must signal the whole process group (or proot directly, TERM then KILL) as `lh`'s `stop_proc` did (`lh` L152-163).
- **Gate D: PASS for this load.** Tree RSS 1.59-1.64 GB (app process ~265-305 MB, server stand-in 458 MB, whisper stand-in 710 MB, `claude` 196 MB), `MemAvailable` 2.70-2.97 GB throughout, no low-memory kill. The real Next server's RSS and the visible WebView UI were not part of this run, and the whisper stand-in goes away now that dictation is decided to be `SpeechRecognizer`.

Findings worth keeping:

- The rootfs tarball is large mostly because of Node (~150 MB unpacked) and Ubuntu; with `claude` left out it is about 94 MB compressed on the phone-built test asset; claude itself adds roughly 130 MB when installed. First run is therefore about 300 MB of downloads in total (rootfs, server, npm).
- proot's `--link2symlink` turns an npm hard link into a symlink with an absolute host path. This is harmless while the files stay where they were created (the claude install lives in the home, which never moves) and fatal after moving a tree: never rename `rootfs` after running package scripts in it; the CI-built rootfs has no such links (`tar --hard-dereference`).
- A first-run flow that stalled while the phone was locked led to a wake lock during setup and a `setup.log` for failures.
- The shell layer used for this work collapses double backslashes in command text; Kotlin regexes are written as raw strings.
